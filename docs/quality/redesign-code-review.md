## 1. Executive Summary

An exhaustive, evidence-backed production code review was conducted on the FemmeFlo mobile application codebase following its comprehensive UI/UX redesign and subsequent bug audit.

The review verified all source code under `src/`, including shared UI components, design tokens, navigation layouts, role workspaces (`(seller)`, `(manager)`, `(admin)`, `(auth)`, `(shared)`), API client infrastructure, mock service data stores, and automated test suites.

### Summary Metrics:
* **Overall Assessment:** **CONDITIONAL GO-AHEAD FOR FIXES; NOT PRODUCTION-READY.** The visual presentation, accessibility semantics, and component restructuring are cleanly realized. However, serious architectural defects exist in route authorization, test decoupling, sensitive token transmission, and concurrency controls.
* **Confirmed Defects:** **8 defects** (2 Critical, 3 High, 3 Medium)
* **Suspected / Potential Defects:** **2 defects** (2 Medium)
* **Maintainability Concerns:** **4 concerns** (4 Low)
* **Critical Blockers:**
  1. **Zero Route Authorization / Client Guards:** `(admin)` and `(manager)` navigators and screens lack role guards; any authenticated seller or deep-link caller can access admin screens and execute admin actions.
  2. **Deceptive Test Suite (100% Decoupled):** The 20 passing automated tests in `src/__tests__/` test private, inline mock functions declared entirely inside the test files. They do **not** import or execute a single line of application source code.
  3. **Sensitive JWT Bearer Token Exposed in URL Query Strings:** `sellerApi.getInvoicePdfUrl` puts the secret authentication token into an unencrypted URL parameter (`?token=...`), violating API contracts and exposing tokens to web server access logs and browser history.
  4. **Complete Absence of Sale Idempotency:** Scenario 6 is completely unbacked in application source code; no `X-Idempotency-Key` or unique transaction token is generated or handled during order submission.

## 3. Critical Findings (Evidence-Backed)

### CRIT-01: Route-Level Authorization & Guards Missing Across Admin & Manager Workspaces
* **Severity:** **CRITICAL** | **Confidence:** **CONFIRMED DEFECT**
* **Affected Files:**
  - `src/app/(admin)/_layout.tsx` (Lines 1-93)
  - `src/app/(admin)/approvals/index.tsx` (Lines 1-180)
  - `src/app/(admin)/inventory/index.tsx` (Lines 1-60)
  - `src/app/(admin)/users/index.tsx` (Lines 1-70)
  - `src/app/(admin)/settings/index.tsx` (Lines 1-90)
  - `src/app/(manager)/_layout.tsx` (Lines 1-85)
  - `src/api/mockService.ts` (Lines 504-565)
* **Code Behavior:**
  Role redirection is exclusively handled in `src/app/index.tsx` during initial cold boot (`if (role === 'SELLER') router.replace('/(seller)')`). Once loaded, none of the sub-navigators (`(admin)/_layout.tsx`, `(manager)/_layout.tsx`) nor their underlying screens inspect `useAuth().role` or enforce authorization.
  Furthermore, in `src/api/mockService.ts`, all admin endpoints (`admin/approvals`, `admin/approvals/:id/approve`, `admin/inventory/receipts`, `admin/users`) execute unconditionally without verifying authorization tokens or the caller's role.
* **Impact:** Any authenticated user with a `SELLER` role who triggers `router.push('/(admin)' as any)` or enters via a deep link / web route `/(admin)/approvals` can approve low-price orders, alter global minimum sale prices in settings, or dispatch warehouse transfers.
* **Reproduction Scenario:**
  1. Sign in as Field Seller (`seller@femmeflo.com`).
  2. In the browser bar on web or via deep link `femmeflo://(admin)/approvals`, navigate to admin approvals.
  3. The screen renders all pending price requests, and tapping "Approve Sale" succeeds.
* **Evidence:**
  `src/app/(admin)/_layout.tsx` contains no auth guard:
  ```tsx
  export default function AdminTabsLayout() {
    return <Tabs screenOptions={{ ... }}> ... </Tabs>;
  }
  ```
* **Recommended Correction:**
  Create an `<AuthGuard allowedRoles={['SUPER_ADMIN']} />` wrapper or implement role checks in `_layout.tsx` using `useAuth()`. If `role !== 'SUPER_ADMIN'`, redirect immediately to `/(auth)/login` or the user's role workspace.

### CRIT-02: Automated Test Suite Disconnected from Application Codebase
* **Severity:** **CRITICAL** | **Confidence:** **CONFIRMED DEFECT**
* **Affected Files:**
  - `src/__tests__/business_rules.test.ts` (Lines 1-390)
  - `src/__tests__/bug_fixes.test.ts` (Lines 1-130)
* **Code Behavior:**
  Both test files test local reimplementations of functions rather than importing application code.

* **Impact:** 20 out of 20 tests pass unconditionally while production code harbors real defects. For example, `checkRolePermission` passes Scenario 7 and 8 in the test suite, but `checkRolePermission` **does not exist anywhere in application source code**. Similarly, Scenario 6 (Idempotency Key) tests a local `Set<string>` inside the test file while the actual mobile order creation has zero idempotency implementation.
* **Evidence:**

  ```ts
  import { describe, it } from 'node:test';
  import assert from 'node:assert/strict';
  // Business Rules & Domain Helpers (defined locally!)
  export function checkRolePermission(...) { ... }
  ```
* **Recommended Correction:**
  Refactor test suites to import genuine application modules: `sellerApi`, `adminApi`, `AuthContext`, and validation helpers.

### HIGH-01: Sensitive JWT Bearer Token Exposed in URL Query Parameters
* **Severity:** **HIGH** | **Confidence:** **CONFIRMED DEFECT**
* **Affected Files:**
  - `src/api/seller.ts` (Lines 218–221)
  - `src/app/(seller)/sales/[id].tsx` (Lines 122–126)
* **Code Behavior:**
  In `sellerApi.getInvoicePdfUrl`:
  ```ts
  async getInvoicePdfUrl(id: string, download = true): Promise<string> {
    const token = await tokenStorage.getToken();
    return `${API_BASE_URL}/invoices/${id}/pdf?download=${download ? 'true' : 'false'}${token ? `&token=${encodeURIComponent(token)}` : ''}`;
  }
  ```
* **Impact:** Exposing JWT access tokens in URL query strings causes them to be logged in reverse proxies, web server access logs (Nginx, Apache, AWS CloudWatch), browser history, and HTTP `Referer` headers. Furthermore, it directly violates Section 2 of `docs/API CONTRACTS.md`: *"Do not include tokens in URLs."*
* **Evidence:**
  `docs/API CONTRACTS.md` line 34: `Do not include tokens in URLs.`
  `src/app/(seller)/sales/[id].tsx` line 126 downloads via `FileSystem.downloadAsync(url, fileUri)` without HTTP headers.
* **Recommended Correction:**
  Pass the token in request headers using `expo-file-system`:
  ```ts
  await FileSystem.downloadAsync(pdfUrlWithoutQueryToken, fileUri, {
    headers: { Authorization: `Bearer ${token}` },
  });
  ```

### HIGH-02: Missing Re-Entry Locks on Mutation Handlers (Double-Tap Vulnerabilities)
* **Severity:** **HIGH** | **Confidence:** **CONFIRMED DEFECT**
* **Affected Files:**
  - `src/app/(seller)/sales/[id].tsx` (`handleCollectPayment`, line 58)
  - `src/app/(admin)/approvals/index.tsx` (`handleApprove` line 63, `handleReject` line 89)
  - `src/app/(admin)/categories/index.tsx` (`handleCreateCategory`, line 64)
  - `src/app/(shared)/change-password.tsx` (`handleSubmit`, line 35)
  - `src/app/(auth)/forgot-password.tsx` (`handleSend`, line 28)
  - `src/app/(auth)/reset-password.tsx` (`handleReset`, line 30)
* **Code Behavior:**
  While `bug-audit-and-fixes.md` reported BUG-003 fixed across POS and customer onboarding, multiple mutation handlers were left without immediate synchronous guards:
  ```ts
  // In src/app/(seller)/sales/[id].tsx
  async function handleCollectPayment() {
    // Missing: if (isCollecting) return;
    setIsCollecting(true);
    ...
  }
  ```
* **Impact:** Rapid consecutive taps before React rerenders the button state can trigger duplicate payment collections, duplicate category creations, and race conditions during order authorization.
* **Recommended Correction:**
  Add synchronous guards `if (isCollecting) return;` or `if (isSubmitting) return;` at the absolute top of each mutation function.

### HIGH-03: Zero Idempotency Implementation in Sale Creation
* **Severity:** **HIGH** | **Confidence:** **CONFIRMED DEFECT**
* **Affected Files:**
  - `src/api/seller.ts` (Lines 179–184)
  - `src/api/client.ts` (Lines 137–173)
  - `src/app/(seller)/sales/new.tsx` (Lines 104–150)
* **Code Behavior:**
  `sellerApi.createSale` accepts a `CreateSalePayload` and sends a plain POST request with no `X-Idempotency-Key` or client-generated request ID. If a network timeout aborts the request after 45 seconds (`client.ts` line 234), the user receives an alert: *"Sale Creation Failed... Please try again."* Tapping "Confirm Sale" sends a new POST request with identical items and no idempotency deduplication key, causing duplicate sales and duplicate stock deductions on the backend.
* **Evidence:**
  `docs/API CONTRACTS.md` Section 2: `X-Idempotency-Key: <unique-uuid>`.
  `src/api/seller.ts` lines 179-184:
  ```ts
  async createSale(payload: CreateSalePayload): Promise<{ sale: SaleItem }> {
    return apiRequest<{ sale: SaleItem }>('seller/sales', {
      method: 'POST',
      body: JSON.stringify(payload),
    });
  }
  ```
* **Recommended Correction:**
  Generate a unique UUID per order draft (e.g. `Crypto.randomUUID()`) and send `X-Idempotency-Key` in headers. In `mockService.ts` and backend, reject or return cached response if key was already processed.

## 6. API Compatibility Review

1. **Verified Contracts:**
   - Auth: `POST /auth/login` (supports role-specific subpaths `seller/auth/login`, `manager/auth/login`, `admin/auth/login`).
   - Customer: `GET /seller/customers`, `POST /seller/customers`, `GET /seller/customers/:id`.
   - POS: `POST /seller/sales`, `GET /seller/sales`, `GET /seller/sales/:id`, `PATCH /seller/sales/:id/payment`.
   - Inventory: `GET /seller/inventory`, `GET /seller/inventory/transactions`, `GET /admin/warehouses`.
   - Attendance: `GET /seller/shifts/current`, `POST /seller/shifts/start`, `POST /seller/shifts/end`.

2. **Contract Mismatches & Concerns:**
   - **Idempotency Header:** `docs/API CONTRACTS.md` specifies `X-Idempotency-Key: <unique-uuid>`. The client fails to provide this header in `sellerApi.createSale`.
   - **Token in URL:** `docs/API CONTRACTS.md` Section 2 explicitly forbids tokens in URLs, yet `sellerApi.getInvoicePdfUrl` appends `?token=...`.
   - **Pagination Metadata:** In `adminApi.listApprovals` and `sellerApi.listCustomers`, server responses return `{ items, pagination }`, while some older routes return `{ customers, pagination }`. The client handles this via `raw?.customers ?? raw?.items ?? []`, which is safe.

3. **Unverified Backend Assumptions (Require Running Server Access):**
   - Whether the production backend accepts `Authorization: Bearer <token>` on binary PDF stream downloads (`/invoices/:id/pdf`).
   - Whether the backend enforces role checks on `/admin/approvals/:id/approve` when accessed by a seller token.
